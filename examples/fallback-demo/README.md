# Fallback Demo

> **Note — reference documentation, not runnable source code.**  
> This folder documents endpoints, toggles, and expected behaviour for the fallback demo service.
> The actual source files are generated by `/scaffold-service` — run it in GitHub Copilot Chat
> and select the capabilities you want (Kafka, Redis, S3). The fallback adapters are always
> included automatically.

Demonstrates toggling fallbacks: Kafka → DB outbox, Redis → JSON file, S3 → local filesystem.

## How fallbacks work

Every capability interface has two wired implementations: a **production adapter** and a **fallback adapter**.
The active adapter is selected at startup based on environment variables:

| Toggle | Values | Effect |
|--------|--------|--------|
| `FALLBACK_KAFKA` | `db` | Writes events to `outbox_message` DB table instead of Kafka |
| `FALLBACK_CACHE` | `jsonfile` | Reads/writes `./data/fallback-cache/cache.json` instead of Redis |
| `FALLBACK_STORAGE` | `local` | Reads/writes `./data/fallback-storage/` instead of S3 |
| `FALLBACK_SECRETS` | `env` | Reads plain env variables instead of Vault/Secret Manager |

Fallbacks are **dev/test only** — never set these in production. Each fallback emits a
`fallback.active{name="<dep>"}` metric and a structured warning log when active.

## Demo endpoints (generated service exposes these)

## Endpoints

| Method | Path | Description |
|--------|------|-------------|
| POST | `/api/messages` | Publishes a message via `MessagePublisher` |
| GET | `/api/cache/{key}` | Reads from `CacheProvider` |
| PUT | `/api/cache/{key}` | Writes to `CacheProvider` with TTL |
| POST | `/api/files/upload` | Uploads a file via `ObjectStorageProvider` |
| GET | `/api/files/{key}` | Downloads a file via `ObjectStorageProvider` |
| GET | `/api/secrets/{key}` | Reads a secret via `SecretProvider` |
| GET | `/actuator/health` | Health check |

## Running

### With All Fallbacks (Zero Infra)

```bash
cd examples/fallback-demo

# Java
FALLBACK_KAFKA=db FALLBACK_CACHE=jsonfile FALLBACK_STORAGE=local FALLBACK_SECRETS=env \
  ./mvnw spring-boot:run

# Python
FALLBACK_KAFKA=db FALLBACK_CACHE=jsonfile FALLBACK_STORAGE=local FALLBACK_SECRETS=env \
  uvicorn src.fallback_demo.main:app --port 8080
```

### With Real Infrastructure

```bash
# Start infra
docker compose -f docker-compose.dev.yml up -d

# Run service (no fallback toggles)
./mvnw spring-boot:run
```

## Testing the Fallbacks

```bash
# Publish a message (goes to in-memory queue)
curl -X POST http://localhost:8080/api/messages \
  -H 'Content-Type: application/json' \
  -d '{"topic": "orders", "body": {"id": "123"}}'

# Write to cache (in-memory HashMap)
curl -X PUT http://localhost:8080/api/cache/test-key \
  -H 'Content-Type: application/json' \
  -d '{"value": "hello", "ttlSeconds": 60}'

# Read from cache
curl http://localhost:8080/api/cache/test-key

# Upload a file (to ./data/fallback-storage/)
curl -X POST http://localhost:8080/api/files/upload \
  -F 'file=@README.md' -F 'key=demo/readme.md'

# Check health
curl http://localhost:8080/actuator/health
```

## What to Observe

| Scenario | Behavior |
|----------|----------|
| Message publish with fallback | Returns 200, message stored in-memory (lost on restart) |
| Cache read with fallback | Returns data from in-memory HashMap with TTL expiry |
| File upload with fallback | File appears in `./data/fallback-storage/demo/readme.md` |
| Secret read with fallback | Reads from environment variables |
| Health check | Returns `UP` regardless of fallback mode |
